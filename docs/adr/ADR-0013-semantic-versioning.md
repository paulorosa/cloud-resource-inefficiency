# ADR-0013: Semantic Versioning with setuptools-scm

## Status
Accepted

## Context

Versionamento manual é **propenso a erros**:
- Desenvolvedor esquece de atualizar `__version__` em `__init__.py`
- Versão em `pyproject.toml` fica desincronizada com `__version__`
- Tag Git é criada, mas `__version__` nunca é atualizado
- Release notes (CHANGELOG) e tags não correspondem

Cenário sem automação:
```python\n# src/cloud_resource_inefficiency/__init__.py\n__version__ = \"0.1.5\"  # Developer forget to update\n\n# Mas tag Git é criada\n$ git tag v0.1.6\n\n# Agora código diz 0.1.5, tag diz 0.1.6 - inconsistência!\n```\n\nBenefício de automação:\n```python\n# setup.py/pyproject.toml com setuptools-scm\n# Versão é derivada de git tags AUTOMATICAMENTE\n# Sem necessidade de atualizar __version__ manualmente\n```\n\n## Decision\n\nAdotar **Semantic Versioning (SemVer)** com **setuptools-scm**:\n\n### SemVer: X.Y.Z (MAJOR.MINOR.PATCH)\n```\n1.0.0: Primeira versão\n1.0.1: Bug fix (patch) → 1.0.0 → 1.0.1\n1.1.0: Nova feature (minor) → 1.0.0 → 1.1.0\n2.0.0: Breaking change (major) → 1.x.x → 2.0.0\n```\n\nRegras:\n- **MAJOR**: Quebra compatibilidade (ex: remover função pública)\n- **MINOR**: Nova feature, backwards compatible (ex: novo provider)\n- **PATCH**: Bug fix (ex: fix em cache logic)\n\n### Tag Git Convention\n```bash\n# Formato: v*.*.* (prefixo 'v')\ngit tag v0.1.0\ngit tag v0.2.0\ngit tag v1.0.0\n\n# setuptools-scm lê tags com padrão v{version}\ngit tag v0.1.0 -m \"Release version 0.1.0\"\ngit push origin v0.1.0\n```\n\n### setuptools-scm Configuration\n```toml\n# pyproject.toml\n[build-system]\nrequires = [\"setuptools>=61.0\", \"setuptools-scm>=8\", \"wheel\"]\nbuild-backend = \"setuptools.build_meta\"\n\n[project]\nname = \"cloud-resource-inefficiency\"\ndynamic = [\"version\"]  # Version é dinâmica (do Git)\nrequires-python = \">=3.9\"\n\n[tool.setuptools_scm]\ntag_regex = \"^v(?P<version>\\\\d+\\\\.\\\\d+\\\\.\\\\d+)$\"\nfallback_version = \"0+unknown\"\n```\n\nComo funciona:\n1. **On Commit**: Versão é gerada como `.dev<commits>` (ex: `0.1.0.dev5`)\n2. **On Tag**: Versão é exatamente a tag (ex: `0.1.0`)\n3. **After Tag**: Versão é tag + dev (ex: `0.1.0.dev3+gXXXXXXX`)\n\n```bash\n# Commit 1 (após v0.1.0)\n$ python -c \"import cloud_resource_inefficiency; print(cloud_resource_inefficiency.__version__)\"\n0.1.0.dev1+gABCD1234\n\n# Commit 10 (após v0.1.0, antes de v0.2.0)\n0.1.0.dev10+gXYZ789AB\n\n# Tag v0.2.0\n0.2.0\n\n# Commit 1 (após v0.2.0)\n0.2.0.dev1+gNEW1234\n```\n\n### Release Workflow\n```bash\n# 1. Editar CHANGELOG.md com mudanças da release\n# 2. Commit CHANGELOG\ngit add CHANGELOG.md\ngit commit -m \"chore: Prepare v0.2.0 release\"\n\n# 3. Criar tag Git (setuptools-scm usa isso)\ngit tag v0.2.0 -m \"Release version 0.2.0\"\ngit push origin main\ngit push origin v0.2.0\n\n# GitHub Actions detecta tag e:\n# - Builds pacote com versão exata v0.2.0\n# - Publica para PyPI\n# - Cria release no GitHub\n```\n\n### No Código: Sem Necessidade de `__version__`\n```python\n# src/cloud_resource_inefficiency/__init__.py\n# ❌ Evitar\n__version__ = \"0.2.0\"  # Redundante! setuptools-scm já sabe!\n\n# ✅ Melhor: Ler de package metadata\ntry:\n    from importlib.metadata import version\n    __version__ = version(\"cloud-resource-inefficiency\")\nexcept Exception:\n    __version__ = \"unknown\"\n```\n\n## Rationale\n\n1. **Zero Friction**: Versão automática a partir de tags Git\n2. **Sem Redundância**: Não duplicar versão em múltiplos arquivos\n3. **Industry Standard**: Todos os projetos sérios usam SemVer\n4. **Clear Intent**: Tag Git é Single Source of Truth\n5. **Automation**: CI/CD automaticamente publica versão correta\n\n## Consequences\n\n### Positive\n- ✅ Impossibilidade de versão em `__version__` desincronizada com tag\n- ✅ Versionamento automático em CI/CD\n- ✅ Histórico claro de releases em Git tags\n- ✅ Usuários podem instalar exata versão: `pip install cloud-resource-inefficiency==0.2.0`\n- ✅ Devs podem testá-la: `cloud-resource-inefficiency==0.2.0.*`\n- ✅ DEV builds tem identidade única (`.dev` suffix)\n\n### Negative\n- ❌ Dependência em setuptools-scm (mas é std em Python)\n- ❌ Git tags requeridas para versionamento (menos flexível)\n- ❌ `__version__` não é hardcoded (devs acham confuso)\n- ❌ Falha se não houver tags Git (fallback para \"0+unknown\")\n\n## Alternatives Considered\n\n### 1. Manual Version Management\n```python\n# __init__.py ou pyproject.toml\n__version__ = \"0.2.0\"\n```\n**Rejeitado**: Propenso a erros. Fácil esquecer de atualizar.\n\n### 2. Calendar Versioning\n```\n2026.08.25  (YYYY.MM.DD)\n2026.08.26\n```\n**Rejeitado**: Menos informativo que SemVer. Não indica breaking changes.\n\n### 3. setuptools-scm + Static Version File\n```toml\n# Ambos: pyproject.toml (dinâmico) + __version__.py (estático)\n# Complexidade desnecessária\n```\n**Rejeitado**: Redundância, sem benefício.\n\n### 4. Commit Hash como Versão\n```\nABCD1234  (git rev-parse --short HEAD)\n```\n**Rejeitado**: Não é versionamento semântico. Confuso para usuários.\n\n## Related Decisions\n\n- **ADR-0014**: GitHub Actions CI/CD automaticamente publica versão\n- **ADR-0013**: setuptools-scm gera versão dinamicamente\n\n## Implementation References\n\n### Key Files\n- `pyproject.toml`\n  - `dynamic = [\"version\"]`\n  - `[tool.setuptools_scm]` config\n- `src/cloud_resource_inefficiency/__init__.py`\n  - `__version__` derivada via `importlib.metadata`\n- `CHANGELOG.md`\n  - Mantém histórico de releases\n  - Mantém SemVer format\n- `.github/workflows/release.yml`\n  - Detecta tags, publica para PyPI\n\n### Release Checklist\n```markdown\n## Release v0.2.0\n\n- [ ] Review pull requests para v0.2.0\n- [ ] Atualizar CHANGELOG.md com todas as mudanças\n- [ ] Verificar versão será correta (setuptools-scm)\n- [ ] Criar commit: \"chore: Prepare v0.2.0 release\"\n- [ ] Criar tag: `git tag v0.2.0 -m \"Release version 0.2.0\"`\n- [ ] Push tag: `git push origin v0.2.0`\n- [ ] Verificar GitHub Actions executou release workflow\n- [ ] Verificar pacote foi publicado em PyPI\n- [ ] Verificar GitHub Release foi criado\n```\n\n### CHANGELOG Format\n```markdown\n# Changelog\n\nTodas as mudanças notáveis neste projeto são documentadas neste arquivo.\n\n## [0.2.0] - 2026-08-26\n### Added\n- Novo recurso X\n- Novo recurso Y\n### Changed\n- Comportamento de Z mudou\n### Fixed\n- Bug em A\n\n## [0.1.0] - 2026-08-25\n### Added\n- Primeiro release\n```\n\n### Version Checks in Tests\n```python\nimport cloud_resource_inefficiency\n\ndef test_version_is_semantic():\n    \"\"\"Verifica que versão segue SemVer\"\"\"\n    import re\n    version = cloud_resource_inefficiency.__version__\n    # Deve ser: X.Y.Z ou X.Y.Z.devN ou X.Y.Z.devN+gXXXX\n    semver_pattern = r\"^\\d+\\.\\d+\\.\\d+(\\.(dev\\d+|a\\d+|b\\d+|rc\\d+))?(\\.post\\d+)?(\\+g[a-f0-9]+)?$\"\n    assert re.match(semver_pattern, version), f\"Invalid version: {version}\"\n```\n\n## Notes\n\n- **Pre-Release Tags**: Suportadas via suffix (ex: `v0.2.0-rc.1`)\n- **PyPI Publishing**: Automático via GitHub Actions\n- **Yanking Old Versions**: Se precisar revogar versão em PyPI: `pip index versions cloud-resource-inefficiency` depois `pip index yank ...`\n- **Local Development**: Em desenvolvimento local, versão terá `.dev` suffix (ex: `0.2.0.dev5`)\n- **Rollback**: Se tag foi criada por engano: `git tag -d v0.2.0; git push origin :v0.2.0`\n"
